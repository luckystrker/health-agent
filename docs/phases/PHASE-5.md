## 1. Цели и границы

### Что входит в фазу
- **Построение тренировочной программы** (`build-program`): wger REST (без ключа) →
  структура (мышцы, оборудование, картинки); имена/описания переводятся агентом на русский
  на лету.
- **Хранение программы** (`workout_programs` + `program_sessions`) и логов выполнения
  (`workout_logs`). План = совокупность строк `program_sessions` для `program_version`;
  колонки `workout_programs.plan` **нет** (см. §11.4).
- **Адаптация** (`reschedule`, `log-workout`) + **триггер адаптации** `program-check`
  (ежедневный schedule): при пропусках/`partial`/`skipped` бот переносит/облегчает/
  пересобирает план (новая `version`). Решение — агент на основе логов. Триггер обязателен:
  без schedule/хука адаптация проактивно не запустится (см. §5.5, §11.4).
- Напоминания о тренировках — потребляются фазой 4 (`workout-reminder`); здесь —
  наполнение `reminder_settings.workout_times` под построенную программу (с подтверждением
  юзера, см. §5.2) и **обновление** `workout_times` при переносе (`reschedule`, см. §5.4).
- Сводка тренировок в недельном отчёте (отчёт — фаза 3; здесь — данные для сводки).

### Что НЕ входит
- Авто-детекция выполнения по данным часов (HR-паттерн → «отработал тренировку») —
  помечено в спеке как «device_detected — отдельной фазой». На v1 выполнение отмечается
  вручную (`log-workout`).
- OpenAPI-коннекция к wger (`defineOpenAPIConnection`) — спека выбрала **свои tools**
  с прямыми `fetch` (§6.3). При имплементации подтвердить достаточность.

### Ключевое архитектурное решение фазы
**Свои tools с прямыми `fetch` к wger REST** (без OpenAPI-коннекции и без auth) — чище для
перевода и фильтрации (§6.3). Русский ≈1% покрытия wger → агент переводит английское
имя+описание на русский на лету (LLM-перевод; в `instructions` явно указать: при выдаче
упражнения переводить название и описание).

## 4. Таблицы БД

Уже созданы (фаза 0). Активно используются:
- `workout_programs` — мета-версия программы (PK `user_id, version`): goal_kind,
  frequency_per_week, equipment[], session_duration_min, constraints, active.
- `program_sessions` — плоская разбивка (день → упражнение → подходы/повторы): PK id,
  `(user_id, program_version, day_of_week, sort_order)` индекс, `wger_exercise_id`,
  `exercise_name_en` (кэш), `sets`, `reps`.
- `workout_logs` — выполнение (`status` completed/skipped/rescheduled/partial,
  `source` manual на v1).
- `reminder_settings.workout_times` — `[{day_of_week, local_time}]` под программу.

## 5. Детали реализации

### 5.1 wger REST (§6.3)
- `https://wger.de/api/v2/` — бесплатный REST, без ключа, без auth (на чтение).
- Эндпоинты: `/exerciseinfo/{id}/` (вложения: muscles, equipment, images, translations).
- Русский ≈1% покрытия → LLM-перевод имени+описания на лету.

### 5.2 `build-program` (§11.4)
- **Вход:** цель (`goals.kind`), частота/нед, длительность сессии, оборудование
  (дом/зал/улица), ограничения (травмы), история активности (из часов за N недель, если
  есть фаза 1).
- **Источник упражнений:** wger (структура: мышцы, оборудование, картинки).
- **Перевод:** агент переводит имя+описание на русский; кэш в `exercise_name_en` (англ.
  имя) + отдаётся юзеру на русском.
- **План:** недельная структура (дни → упражнения → подходы/повторы) → новая версия
  `workout_programs` + строки `program_sessions` (предыдущая `active=false` в той же
  транзакции). План = совокупность строк `program_sessions`; колонки `.plan` нет (§11.4).
- **Напоминания (`reminder_settings.workout_times`) — с подтверждением юзера (HITL):**
  - Если у юзера уже есть непустые `workout_times` (онбординг шаг 9, §10 / `set-reminders`,
    §8) — `build-program` **не перезаписывает их молча**. Перед записью агент показывает
    предложенные дни/времена под программу и спрашивает: «заменить твои текущие
    напоминания о тренировках?» (inline-кнопки «Заменить» / «Оставить мои» / «Смешать»).
  - «Заменить» → `workout_times` = дни/времена программы; «Оставить мои» → не трогать;
    «Смешать» → объединить (дубли по `(day_of_week, local_time)` удалить).
  - Если `workout_times` пустые — записать предложенные без вопроса.
  - Формат `workout_times`: `[{day_of_week, local_time}]`, `day_of_week` 0=вс…6=сб
    (как `program_sessions.day_of_week` §5.5; см. §5.6), `local_time` "HH:MM" в tz юзера.

### 5.3 `log-workout` (§8, §11.4)
- Отметить выполнение сессии плана: `status` **completed / skipped / partial** (три статуса
  — `rescheduled` проставляется инструментом `reschedule`, а не `log-workout`; см. §5.4 и
  глобал §8).
- Заполняет `scheduled_day` (день плана, к которому относится сессия), `performed_at`,
  `notes`, `source='manual'` на v1 (device_detected — отдельной фазой).
- Валидация: `scheduled_day` должен существовать в активной программе (есть
  `program_sessions` с таким `day_of_week`); иначе user-friendly сообщение.

### 5.4 `reschedule` (§11.4) — механика переноса и sync напоминаний
`reschedule` вызывается (а) юзером вручную, (б) агентом из proactive-сессии триггера
`program-check` (§5.5). Возможные действия:
1. **Перенос тренировки на другую дату/день недели.**
   - Исходная сессия: создаётся строка `workout_logs` со `status='rescheduled'`,
     `scheduled_day` = исходный день, `performed_at = now()` (фиксация факта переноса).
   - Новая сессия: `program_sessions` обновляется (или добавляется строка с новым
     `day_of_week` для текущей `program_version`), представляющая перенос на новый день.
     Либо, если перенос — разовое исключение (не изменение регулярного расписания), новая
     сессия не создаётся в `program_sessions`, а фиксируется как «разовый до-бавочный день»
     через `workout_logs` с `scheduled_day` = новая дата и `status='pending'`-семантикой
     (см. Примечание ниже).
   - **Sync напоминаний (обязательно):** `reschedule` обновляет
     `reminder_settings.workout_times` под перенос (убирает старый `(day_of_week,
     local_time)`, добавляет новый), иначе `workout-reminder` фазы 4 продолжит напоминать
     по старому дню. Если перенос — разовое исключение, `workout_times` можно не менять
     (напоминание по регулярному расписанию остаётся).
2. **Облегчение тренировки** — изменяются `sets`/`reps` в `program_sessions` текущей
   активной `program_version` (без новой версии). `workout_logs` — `status='partial'`
   через `log-workout`, либо просто фиксируется notes.
3. **Пересборка плана** — новая `version` `workout_programs` (прежняя `active=false`) +
   новый набор `program_sessions`. `reminder_settings.workout_times` обновляется под новое
   расписание (с подтверждением, как в §5.2, если у юзера были свои значения).

> **Примечание о «разовом vs регулярном» переносе.** `program_sessions` описывает
> **регулярное** недельное расписание (`day_of_week`). Разовый перенос (юзер заболел,
> сделает в другой день) не должен менять регулярный план. Контракт: для разового переноса
> `reschedule` создаёт `workout_logs` со `status='rescheduled'` (исходный день) и не трогает
> `program_sessions`; новая дата — через `scheduled_day` в логе + напоминание в этот день
> может быть отправлено как разовое (через dispatcher). Для регулярного изменения
> (постоянный перенос на другой день недели) — правится `program_sessions` и `workout_times`.
> Решение о типе переноса принимает агент (или уточняет у юзера). Зафиксировать реализацию в
> STATUS.md.

### 5.5 Триггер адаптации — `program-check` (§11.4)
- Schedule, cron `0 5 * * *` (ежедневно), идёт в dispatcher'е с `userAuthFor`, как другие
  schedules (§9). Для каждого онборженного юзера с активной программой (`workout_programs
  .active=true`).
- Проверяет `workout_logs` (за последние 7 локальных дней) на признаки отставания:
  - есть запланированные на прошедшие дни сессии без записи в `workout_logs`
    (`status IS NULL` — сессия не отмечена);
  - накоплено ≥2 `status='skipped'` или `status='partial'` за последние 7 дней.
- При срабатывании — proactive-сессия с `userAuthFor(u)`: агент анализирует логи + цель и
  решает (перенос / облегчение / пересборка), вызывая `reschedule`. Тон — по пресету юзера.
- **Не дублирует anomaly-check** (§11.5) — тот покрывает сон/калории/шаги/вес, не тренировки.
- Дополнение: блок «как идёт программа» в недельном отчёте (фаза 3) может рекомендовать
  адаптацию — это дополняет, но не заменяет `program-check`.

## 6. Edge-cases (см. §11.4, §16)

- **wger даун / 429 / сеть** — retry с экспоненциальным backoff; при провале —
  user-friendly сообщение; не валить построение молча.
- **Нет упражнений под фильтр** (редкое оборудование + ограничения) — сообщить юзеру,
  предложить ослабить фильтр.
- **Конфликт переводов** — упражнение может иметь в wger частичный русский перевод
  (`translations`); приоритет: если есть качественный RU-translation — брать его, иначе
  LLM-перевод английского.
- **Параллельные `build-program`** — одна активная версия на user; новая делает прежнюю
  `active=false` в одной транзакции.
- **`log-workout` для несуществующего `scheduled_day`** — валидация, user-friendly
  сообщение.

## 7. Критерии готовности

- [ ] `build-program` строит недельную программу под вход (цель/частота/оборудование/
      ограничения), записывает новую активную версию, прежняя → `active=false` в одной
      транзакции; план = строки `program_sessions` (колонки `.plan` нет).
- [ ] Упражнения отдаются на русском (перевод LLM или wger-RU translation); английское
      имя кэшируется в `exercise_name_en`.
- [ ] `build-program` при наличии непустых `workout_times` спрашивает подтверждение
      (Заменить / Оставить мои / Смешать); при пустых — записывает без вопроса.
- [ ] `log-workout` фиксирует **3 статуса** (completed/skipped/partial); `rescheduled`
      проставляется только через `reschedule`.
- [ ] `reschedule`: перенос (разовый — `workout_logs.status='rescheduled'` без правки
      `program_sessions`; регулярный — правка `program_sessions` + `workout_times`),
      облегчение (правка `sets`/`reps` текущей версии), пересборка (новая `version`).
      **В случае регулярного переноса/пересборки `reminder_settings.workout_times`
      обновляется** (иначе `workout-reminder` фазы 4 продолжает звать на старый день).
- [ ] `program-check` (cron `0 5 * * *`) для каждого онборженного юзера с активной
      программой детектит отставание (≥2 skipped/partial или незалогированные сессии за
      7 дней) и запускает proactive-сессию → `reschedule`. Изоляция per-user.
- [ ] `reminder_settings.workout_times` в формате `[{day_of_week: 0=вс..6=сб, local_time:
      "HH:MM"}]` (синхронизировано с `program_sessions.day_of_week`).
- [ ] Обработка ошибок wger (сеть/даун) — user-friendly, без стеков.
- [ ] Журнальная запись в STATUS.md о завершении фазы 5.

## 8. Риски и проверяемые гипотезы

- **wger: свои tools vs OpenAPI-коннекция** (откр. вопрос §20.4): в спеке выбраны свои
  tools; при имплементации подтвердить достаточность, либо завернуть
  `/api/v2/exerciseinfo/` в `defineOpenAPIConnection` если нужен более широкий поиск.
- **Качество LLM-перевода упражнений (эвал)** — подобрать промпт/инструкцию; зафиксировать
  в `instructions.md` правило «при выдаче упражнения переводить название и описание».
  Измеримый критерий перевода (вместо нечёткого «начать собирать эвалы», §18.3): на
  выборке ≥30 упражнений (разные группы мышц) — ≥90% корректных переводов по ручной оценке
  (название + описание понятны русскоязычному юзеру), ≤5% — с критическими ошибками
  (неверное упражнение/безопасность). Эвал собирается в этой фазе как scripts/evals, а не
  блокирующий DoD.
- **Триггер адаптации `program-check`** — проверить, что proactive-сессия с `userAuthFor`
  корректно доходит до агента и `reschedule` вызывается (см. риск в
  [`PHASE-3.md`](./PHASE-3.md), §8 про dispatcher). Не дублирует anomaly-check (сон/калории/
  шаги/вес).
- **Разовый vs регулярный перенос** — контракт в §5.4 (Примечание); решение о типе
  переноса принимает агент/уточняет у юзера. Зафиксировать UX-флоу в STATUS.md.
- **Стабильность wger (anti-bot на web, но REST открыт)** — REST должен быть стабилен;
  проверить rate-limiting и при необходимости добавить кэш/retries.
- **`wger_exercise_id` foreign-key?** — спека не накладывает FK (внешний источник);
  подтвердить, что храним просто int.
