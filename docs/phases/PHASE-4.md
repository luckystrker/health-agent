## 1. Цели и границы

### Что входит в фазу
- **Daily-напоминалки** (утро/день/вечер) — fuzzy-окно совпадения с локальным временем
  юзера, loop по `users`.
- **Workout-reminder** — почасовой джоб, сверка `reminder_settings.workout_times` с
  текущим локальным временем.
- **Anomaly-check** — каждые 30 мин, проверка порогов аномалий → алерт (с rate-limit:
  не чаще 1 алерта типа на юзер×день).
- Полномерное использование dispatcher'а (заложен в фазе 3) во всех schedules.
- `lib/anomalies.ts` — пороги и логика срабатывания.

### Что НЕ входит
- Динамический schedule-store (`patterns/dynamic-scheduling.md`) — на v1 избыточен для
  family-of-2; статичные cron'ы + loop. Масштабирование (>~10 юзеров) — отдельная фаза
  (см. PHASE-6.md и §20.5).
- Алерты оператору (внешний алертинг) — фаза 6.

### Ключевое архитектурное решение фазы
Все schedules ходят от `appAuth`; per-user сообщения — через dispatcher с синтезированным
`userAuthFor(u)` (см. [`PHASE-3.md`](./PHASE-3.md), §5.1). Для точности per-user
напоминаний используется **симметричное fuzzy-окно + dedup** (§5.1): все daily-джобы и
workout-reminder тикают каждый час и при каждом тике проверяют `min(|LT − slot|, 24h − |LT − slot|) ≤ 30 мин`
в локальном времени юзера; повторные срабатывания в ту же локальную дату подавляются
dedup-счётчиком. Почему ежедневно-разовый тик не подходит — см. §5.1.

## 4. Таблицы БД

Новых таблиц нет. Используются:
- `reminder_settings` (`morning_local`, `midday_local`, `evening_local`, `workout_times`
  — `day_of_week`: 0=вс … 6=сб, `local_time`: "HH:MM" в tz юзера; см. §5.6).
- `daily_aggregates` — **только завершённые дни** (базовая линия, скользящие средние).
  Текущий день в агрегате отсутствует (см. §12.3 «Свежесть для anomaly-check»).
- `raw_samples` — текущий день для anomaly-check (сон за прошлую ночь, шаги/активность/
  калории «сегодня»), отфильтрованные по локальному дню юзера.
- `food_entries` (потребление «сегодня») + `lib/calories.ts` (цель — **не** LLM-tools; tools
  вызывает модель, anomaly-check — чистый код, см. §11.5).
- `weight_log` (вес — **не** `daily_aggregates`; в агрегате метрики веса нет).
- `users` (`timezone` для локального времени; `tone_preset`; `blocked` — колонка заведена
  в §5.1, фаза 0; здесь — применяется во всех schedules; `onboarded_at` — фильтр онборженных).

## 5. Детали реализации

### 5.1 Fuzzy-окно (симметричное + dedup) — §9
При каждом тике (UTC) для каждого онборженного юзера:
1. `LT = now() AT TIME ZONE users.timezone` (с днём недели и локальной датой).
2. Срабатывает, если `min(|LT − slot|, 24h − |LT − slot|) ≤ δ`, `δ = 30 мин` на v1.
   Симметричное окно `[slot − δ, slot + δ)` — слот срабатывает **до ±30 мин**, а не
   «после тика с опозданием». Сравнение по модулю суток (для слотов через полночь).
3. **Dedup (обязателен):** хранить «последнее срабатывание» и не слать повторно:
   - daily-джобы: ключ `(user_id, kind, local_date)` где `kind ∈ {morning,midday,evening}`;
   - workout-reminder: ключ `(user_id, program_version, scheduled_local_date)` или
     `(user_id, day_of_week, local_date)`.
   - Счётчик в памяти процесса; при рестарте обнуляется (допустим редкий повторный алерт в
     день рестарта — лучше пропуска; это признанный компромисс, не «память достаточно»).
4. При `δ = 30 мин` и тике в минуту 0 каждого часа окна стыкуются ровно в `HH:30` —
   покрытие 100%, дублей нет (с учётом dedup).

> **Почему daily-джобы ходят каждый час, а не раз в сутки.** Разовый тик в фиксированный
> UTC-час не покрывает слоты юзеров в разных tz (напр. morning 08:00 Europe/Moscow = 05:00
> UTC никогда не совпадёт с тиком 07:00 UTC). Для family-of-2 лишняя нагрузка копеечная;
> при росте — динамический schedule-store (§20.5).

### 5.2 Daily-напоминалки
- `daily-morning` / `daily-midday` / `daily-evening` — каждый почасовой тик (`0 * * * *`),
  fuzzy-сверка по §5.1.
- **Только онборженные юзеры** (`users.onboarded_at IS NOT NULL`), не `blocked` — как в §9
  (`onboardedUsers()`). Без этого фильтра юзер, прервавший онбординг на шаге 9 (напоминания
  уже в `reminder_settings`, `onboarded_at` ещё NULL — см. [`PHASE-0.md`](./PHASE-0.md)
  §6.4), получит напоминалки без контекста.
- `daily-morning`: morning slot → «внести ужин/взвеситься».
- `daily-midday`: midday slot.
- `daily-evening`: evening slot, итог дня по калориям/шагам (текущий день — из `raw_samples`
  + `food_entries`, не из агрегата; см. §4).

### 5.3 Workout-reminder (§9)
- Cron `0 * * * *` (почасово).
- Для каждого онборженного юзера: сверяет `reminder_settings.workout_times`
  (`[{day_of_week, local_time}]`, `day_of_week` **0=вс … 6=сб** — та же нумерация, что в
  `program_sessions.day_of_week` §5.5; см. также §5.6) с текущим локальным днём недели +
  временем (fuzzy по §5.1).
- Совпадение → напоминалка о тренировке (с tone-пресетом). Dedup — по
  `(user_id, day_of_week, local_date)`.

### 5.4 Anomaly-check (§11.5 — полная формулировка там, источник правды)
- Cron `*/30 * * * *` (каждые 30 мин). Для каждого онборженного юзера.
- **Источники данных:**
  - текущий день (сон за прошлую ночь, шаги/активность/калории «сегодня»): `raw_samples`,
    фильтр по локальному дню юзера. Агрегат текущего дня НЕ существует (§12.3).
  - завершённые дни (базовая линия, медианы): `daily_aggregates`.
  - вес: `weight_log` (в агрегате метрики веса нет).
  - цель по калориям: `lib/calories.ts` (фаза 2), НЕ `get-target-calories` tool.
- **Пороги (дефолты, настраиваются в коде, с guard на минимум измерений):**
  - **Сон:** длительность < 5ч **или** `bedtime_local > "02:00"` (по завершённой сессии
    `sleep_session` с `wake_at`; не алертим «нет данных» — это §12.2).
  - **Калории:** `sum(food_entries.kcal, today_local) > target_kcal × 1.25` **и** день не
    окончен (время < конца суток в tz). `target_kcal` — из `lib/calories.ts`.
  - **Активность:** шаги сегодня (`raw_samples`, sum по buckets) **< 50%** медианы шагов за
    последние 7 завершённых локальных дней (`daily_aggregates`, по доступным дням). Guard:
    алерт после 18:00 локально и при ≥3 днях в базовой линии.
  - **Вес:** `|weight_now − prev| / prev > 2.5%` (или `|delta| > 1 кг`), `prev` — медиана
    последних 7 измерений (минимум 3). Source: `weight_log`. Guard: ≥3 измерений за 30 дней.
    Информационно, не тревожно.
- **Rate-limit:** не чаще 1 алерта типа на `(user_id, type, local_date)`. Счётчик — в памяти
  процесса; при рестарте обнуляется (см. §5.1 компромисс; при масштабировании — таблица).
- Тон алерта — по `users.tone_preset`.

### 5.5 Изоляция и обработка ошибок (§16)
- try/catch **per-user** во всех schedules: один сбойный юзер не роняет остальных.
- БД timeout → retry на следующем тике cron, warn-лог, не ронять процесс.
- Telegram 429 → экспоненциальный backoff, warn-лог, не спамить.
- Telegram 403 (юзер заблокировал бота) → `users.blocked = true` (колонка в §5.1 с фазы 0),
  пропускать в будущих рассылках, info-лог.

## 6. Edge-cases (см. §11.5, §12.1, §16)

- **Смена tz юзером (поездка)** — напоминания хранятся в local time, применяются к новому
  tz без изменений (§12.1). Anomaly-check считается по новому tz; переходный день может
  быть «дробным».
- **DST-переход** — локальное время пересчитывается через tz-библиотеку; fuzzy-окно
  корректно охватывает сдвиг.
- **Юзер заблокировал бота** — `blocked=true`, пропускать.
- **Нет данных с часов** — anomaly-check пропускает пороги, требующие данных; не падает.
- **Спам-защита** — rate-limit 1 алерт/тип/юзер×день (см. §11.5).
- **Пропуск напоминания при отсутствии slot'а** — если у юзера `morning_local IS NULL`,
  пропустить, не падать.

## 7. Критерии готовности

- [ ] `daily-morning/midday/evening` ходят каждый час и срабатывают по симметричному
      fuzzy-окну (`min(|LT − slot|, 24h − |LT − slot|) ≤ 30 мин`) в локальном времени юзера;
      **только для онборженных** (`onboarded_at IS NOT NULL`) и не `blocked`; dedup не пускает
      второй алерт того же kind в ту же локальную дату; текст в tone-пресете; изоляция per-user.
      Тест: слот 18:15 local срабатывает (не теряется между тиками 18:00/19:00).
- [ ] `workout-reminder` сверяет `reminder_settings.workout_times` (`day_of_week` 0=вс…6=сб,
      `local_time` "HH:MM") с локальным днём/временем; срабатывает в симметричное окно;
      dedup по `(user_id, day_of_week, local_date)`.
- [ ] `anomaly-check` детектит все 4 порога на фиксирующих тест-кейсах (с конкретными числами
      из §5.4: сон <5ч / bedtime >02:00; калории >target×1.25 и день не окончен; шаги <50%
      7-дневной медианы + guard 18:00/≥3 дня; вес ±2.5% или ±1 кг + guard ≥3 измерений);
      rate-limit не пускает второй алерт того же типа в ту же локальную дату; при отсутствии
      данных — пропускает (не падает, не спамит «нет данных»).
- [ ] Сбой одного юзера не роняет loop; БД-timeout → retry на следующем тике; процесс не
      падает.
- [ ] Telegram 429/403 обрабатываются (backoff + `users.blocked = true`).
- [ ] Юнит-тесты: `anomalies.ts` — каждый порог с положительным/отрицательным кейсом и
      guard'ами (минимум измерений, время суток); fuzzy-сверка (слоты через полночь, DST).
- [ ] Журнальная запись в STATUS.md о завершении фазы 4.

## 8. Риски и проверяемые гипотезы

- **Точность fuzzy-окна ±30 мин** — для family-of-2 приемлемо; при росте аудитории перейти
  на динамический schedule-store (§20.5) для минутной точности и снижения нагрузки (не
  опрашивать всех каждый тик). Зафиксировать переход в STATUS.md когда станет актуально.
- **Rate-limit в anomaly-check / dedup в памяти процесса** — при рестарте (systemd
  `Restart=always`, деплой) счётчик обнуляется → возможен второй алерт того же типа в день
  рестарта. Это **признанный компромисс** (лучше редкого дубля, чем пропуска), а не
  утверждение «память достаточно». При росте числа юзеров / требования strictly-once —
  таблица `alert_log(user_id, type, local_date)` (фаза масштабирования).
- **Тон в алертах** — убедиться, что tone-пресет доезжает в scheduled-сессии (см. риск в
  [`PHASE-3.md`](./PHASE-3.md), §8).
