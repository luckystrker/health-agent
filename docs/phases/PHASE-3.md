## 1. Цели и границы

### Что входит в фазу
- **Недельный отчёт** (`agent/schedules/weekly-report.ts`): раз в неделю per-user сессия
  с синтезированным user-auth → анализ 7 завершённых локальных дней → текст + PNG-график.
- **Графики** (`agent/tools/report/render-chart.ts`): `chartjs-node-canvas` → PNG локально
  (данные не покидают сервер) → `sendPhoto` в Telegram.
- **Tone-пресеты** в деле (на фазе 0 пресеты заведены; здесь — в отчётах и анализе).
- Динамическая инструкция `user-context.ts` (профиль+тренды юзера на `turn.started`).
- Dispatcher-паттерн для per-user сообщений из schedules (`to(telegram,...).send(...,
  { auth: userAuthFor(u) })`) — фундамент для всех schedules (фазы 3 и 4).

### Что НЕ входит
- Daily-напоминалки (утро/день/вечер), workout-reminder, anomaly-check → **фаза 4**
  (используют тот же dispatcher, что здесь заложен).
- Тренировки/программа в отчёте → **фаза 5** (но сводка тренировок берётся из БД, если
  есть данные).
- Адаптивный пересмотр цели — спека говорит «не меняет цель молча»; flag-on-sustained-
  deviation сообщение попадает в отчёт здесь, но пересчёт не делаем.

### Ключевое архитектурное решение фазы
Schedules в eve запускаются от `appAuth` (`principalType: "runtime"`) — это НЕ
пользовательский principal. Любой tool с `requireUser` упадёт. Поэтому **все per-user
сообщения** отправляются через единый dispatcher, синтезирующий user-auth
(`userAuthFor`, заложен в фазе 0) и шлющий отдельную proactive-сессию (§9).

Данные для отчётов бот читает из **нашей БД** (`daily_aggregates`, `food_entries`,
копии логов) — НЕ дёргает FatSecret user-API в фоне (§9, важное следствие).

## 5. Детали реализации

### 5.1 Dispatcher (§9, код-блок в спеке)
```ts
function userAuthFor(u: { telegram_chat_id: bigint; user_id: string }) {
  return {
    authenticator: "telegram-webhook",
    principalId: `telegram:${u.telegram_chat_id}`,
    principalType: "user" as const,
    attributes: { chat_id: String(u.telegram_chat_id), user_id: u.user_id },
  };
}
for (const u of onboardedUsers()) {
  waitUntil(
    to(telegram, { chatId: String(u.telegram_chat_id) }).send(prompt, {
      auth: userAuthFor(u),
    }),
  );
}
```
Внутри такой сессии `requireUser(ctx)` отработает корректно. Изоляция: try/catch per-user
(один сбойный юзер не роняет обработку остальных).

### 5.2 Недельный отчёт (§11.1)
- Сбор данных за **7 завершённых локальных дней** по `daily_aggregates` (локальный день =
  по `users.timezone`).
- Если данных < N из 7 (по умолчанию N=4) — отчёт **генерируется**, но содержит явное
  «нет данных за X дней».
- **Содержание:** сводка трендов:
  - сон: средняя длительность, тренд vs предыдущая неделя;
  - шаги: среднее;
  - вес: дельта;
  - калории: средний баланс vs цель;
  - тренировки: выполнено/пропущено (если есть логи).
- **Выводы и советы** — анализ LLM на основе трендов и цели.
- **График:** один-два PNG (напр. сон по дням + тренд веса) через `render-chart` →
  `sendPhoto`.
- Формат: **тренды + выводы**, без разбора каждого дня по отдельности.
- Тон — по `users.tone_preset`.

### 5.3 Графики (§8, §13)
- `chartjs-node-canvas` локально → PNG → `sendPhoto`.
- Данные здоровья/питания не уходят наружу (privacy).
- При ошибке рендера — фолбэк на текстовую сводку без графика + error-лог (§16).

### 5.4 Динамическая инструкция `user-context.ts` (§4)
- На `turn.started` подгружает профиль + ключевые тренды юзера (краткая сводка), чтобы
  модель имела контекст в каждой интерактивной сессии.
- Не дублировать tonе-инструкцию (она — в `tone.ts`).

### 5.5 Schedule cron
- `weekly-report`: `0 10 * * 1` (UTC) — §9. Время UTC; локальная дата юзера учитывается
  при сборе «7 завершённых локальных дней».

## 6. Edge-cases (см. §11.1, §16)

- **Мало данных за неделю** (<N дней) — отчёт строится с пометкой о неполноте.
- **Нет данных вообще** (новый юзер, ни одного агрегата) — корректное сообщение
  «данных пока недостаточно для отчёта».
- **Ошибка рендера графика** — фолбэк на текстовую сводку, error-лог.
- **Telegram 429** (rate limit) — экспоненциальный backoff, warn-лог (на фазе 4 это
  касается всех schedules; здесь — минимум для weekly-report).
- **Telegram 403** (юзер заблокировал бота) — `users.blocked = true` (колонка заведена в
  §5.1 / миграциями фазы 0; `weekly-report` здесь начинает её проставлять при 403),
  пропускать в будущих рассылках; info-лог. Фаза 4 применяет флаг во **всех** schedules
  (dispatcher фильтрует `blocked=false`).
- **Сбой в одном user-loop** — try/catch per-user, не ронять остальных (§16).
- **Сон через полночь** — корректно отнесён к дате пробуждения (заложено в фазе 1;
  отчёт читает уже корректные агрегаты).

## 7. Критерии готовности

- [ ] `weekly-report` cron срабатывает раз в неделю; для каждого онборженного юзера
      формируется и отправляется отчёт (текст + хотя бы один PNG) в его tone-пресете.
- [ ] Данные собираются за 7 завершённых локальных дней; при <N днях отчёт строится с
      пометкой.
- [ ] `render-chart` рендерит сон/вес (и др.) в PNG; при ошибке — текстовый фолбэк.
- [ ] Dispatcher изолирует сбой per-user (один сбойный юзер не валит остальных).
- [ ] `user-context.ts` подгружает профиль/тренды на `turn.started` (проверяется в
      интерактивной сессии).
- [ ] Юзер видит разницу «по боту» vs «по часам» в контексте калоража (через
      `get-target-calories` фазы 2).
- [ ] Эвал (LLM): качество отчёта (тренды корректны, советы релевантны цели); tone
      выдержан (§18.3 — начать собирать).
- [ ] Журнальная запись в STATUS.md о завершении фазы 3.

## 8. Риски и проверяемые гипотезы

- **Dispatcher под `appAuth`** — свериться с eve-докой (`patterns/dynamic-scheduling.md`,
  `guides/...`) что `to(channel).send(msg, { auth })` синтезирует корректную сессию и
  `requireUser` внутри неё отрабатывает. Это критичный контракт для всех schedules.
- **Статичный cron vs точность локального времени** — weekly-report ходит по UTC
  понедельник 10:00; для family-of-2 это приемлемо (§9). Daily-точность — фаза 4.
- **`chartjs-node-canvas` под Node 24 + systemd** — проверить, что canvas-бэкенд
  рендерит без X-сервера и не падает при рестарте процесса.
- **Tone в анализе LLM** — убедиться, что tone-пресет доезжает до модели именно в
  scheduled-сессии (динамическая инструкция на `turn.started` должна срабатывать и в
  синтезированной user-auth сессии).
- **Эвалы** (§18.3): начать собирать на фазе 3 — качество отчёта, tone, перевод
  упражнений (последнее — фаза 5).
